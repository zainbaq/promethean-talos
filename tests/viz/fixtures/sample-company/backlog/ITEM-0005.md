## Description

Why P3: a small usability wrinkle inside charter scope (Settings screen, criterion 3); stored data is never corrupted and reload shows the right values, so it does not block the goal. Architect note on ITEM-0002 (EVT-20261028173027-fac6): render() in app/settings.js re-reads settings and rewrites every input, so if the user has typed an invalid value in the break field (say 61, kept on screen with the error message per SPEC-0002) and then taps a focus stepper or the sound switch, the break field snaps back to the stored value and the error message disappears mid-correction. Scope: app/settings.js and tests/test_settings.py. How render() should treat a field that is currently invalid is the Chief Architect's call.

## Acceptance criteria

- [ ] fill #break-minutes with 61 (it shows aria-invalid="true" and the rule sentence), then click #focus-inc: #focus-minutes reads 26 and stored focusMinutes is 26; #break-minutes still reads 61 with aria-invalid="true", its section still has data-invalid="true" and the help text is still the rule sentence; stored breakMinutes is unchanged (5).
- [ ] fill #focus-minutes with 0, then click #sound-toggle: aria-checked flips and is stored; #focus-minutes still reads 0 with aria-invalid="true"; stored focusMinutes is unchanged (25).
- [ ] After page.reload() both inputs show the stored values (26 and 5 in the first flow) with no invalid state.
- [ ] All existing tests in tests/test_settings.py pass and axe reports 0 serious or critical violations on settings.html in light and dark.
