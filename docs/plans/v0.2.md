# Talos v0.2 plan

Status: draft for CEO review · 2026-10-26 · Author: Claude (Opus 5.5) for Zain (CEO)

## 1. Goals

1. **Spend fewer tokens per shipped item**, measured, not guessed.
2. **Ship much better frontends**: a design system and visual direction up front, and agents that look at what they built.
3. **Add a productization team** that turns a working app into something a customer can buy.
4. **Add a GTM team** that owns customer profile, positioning, pricing and launch, and never sends anything on its own.
5. Keep small projects small: teams are **opt-in per charter**.

## 2. Baseline: where the linkboard run spent its tokens

What it says:

- **Fable is 86% of tokens read and 81% of output.** Execution on Sonnet is about 8%.
- **The main session alone is 58%.** It averaged about 106k tokens of context per call, because one long conversation ran every phase and re-read its growing history on each turn.
- **Engineering is not the cost.** Engineers used 2.6%. "Plan high, execute low" works on the execution side; the planning side is the bill.
- The Chief Architect is the largest subagent: long spec drafting plus rework rounds when acceptance lines were wrong.

So the levers, in order: shrink the orchestrator's context, move routine Fable work down a tier, give every role a smaller context, then trim review.

## 3. Workstreams

### A. Measure (first; everything else is judged by it)

- **A1. `talos usage`.** New CLI command. Parses the project's transcripts, maps subagents to roles via `.meta.json`, dedupes streamed messages by id, and buckets usage into cycles using the ledger's cycle start and end timestamps. Output: the table above, per cycle, and per item where the dispatch prompt names an item id. Stdlib only. The transcript format is not a public contract, so the parser fails soft ("usage unavailable") and is covered by a fixture test.
- **A2. Report and budget.** `talos report` gains a "Spend" section: tokens by tier, the top three roles, tokens per verified item. Charters may set the cycle budget in tokens. `talos status` shows the measured figure, so the Chief of Staff stops on a number, not an estimate.
- **A3. Retro input.** The retro reads `talos usage` and must name the most expensive role of the cycle and why.

Done when `talos usage` on the linkboard project reproduces the table above within rounding, and a fresh cycle report shows a Spend section.

### B. Spend less

- **B1. Short-lived orchestration.** The main session stops carrying the whole cycle. `/talos-cycle` becomes a loop of phases (dispatch, collect, review, verify, report). Each phase runs as a fresh `chief-of-staff` subagent that starts from `talos status --brief` plus the phase's inputs and ends with a hand-back. The main session holds only those hand-backs. Expected to cut the largest line in the table by more than half; measured, not assumed.
- **B2. Tier the routine work down.** Add a Sonnet `coordinator` role that runs mechanical phases exactly as the skill says: dispatch from an approved selection, log hand-backs, collect reviews, render reports. Fable `chief-of-staff` keeps selection, escalation, budget calls and the CEO-facing summary. The Learning Officer splits: a Sonnet pass mines the ledger into candidate lessons, and Fable accepts, merges or rejects them.
- **B3. Context packs.** `talos context ITEM-xxxx --role <role>` writes one file with exactly what that role needs: the item, its spec, linked ADRs, the environment lines that matter, and the top lessons by tag. Dispatch prompts point at the pack instead of telling roles to read the record. Roles are forbidden from reading the whole `company/` tree.
- **B4. Review by risk.** The Chief Architect sets `risk: low | normal | high` on each item. Low (docs, config, copy) skips the Opus reviewers and goes straight to verification. Security review runs on high items and on items touching auth, credentials, user input, ingestion or external APIs. That is already the rule; now a field drives it instead of judgment.
- **B5. Fewer rework rounds.** `talos spec lint SPEC-xxxx` checks the handoff contract mechanically before an engineer sees the spec: length budget, every acceptance line has a command and expected result or is marked UNEXECUTED, files in scope exist or are marked new, linked ADRs exist.
- **B6. Prompt hygiene.** Role files get a hard length budget of about 40 lines. Stable text goes first and per-item text last, so the cached prefix is reused. Dispatch prompts set turn caps per role.

Target: 40% fewer tokens per verified item than the linkboard baseline on a comparable brief. That is a hypothesis for the replay test in section 4, not a promise.

### C. Design team (frontends)

The problem: UI quality is visual, and a text spec followed exactly by Sonnet produces generic screens. Agents also never look at what they built.

| Role | Model | Does |
|---|---|---|
| Head of Design (new) | Fable | Visual direction, design system, one distinctive idea per product, critiques screenshots against the direction. Never writes UI code. |
| UX Designer (revised) | Sonnet | Flows, screen specs, states and exact copy, inside the design system. |
| UI Engineer (new) | Sonnet | Frontend implementation only. Screenshots its own screens before hand-back. |
| Design QA (new) | Sonnet | Playwright screenshots at phone and desktop widths, light and dark; accessibility (axe) and Lighthouse runs; files the evidence. |

Artifacts in `company/design/`:

- `direction.md`: mood, references the CEO supplied, the distinctive idea, what to avoid.
- `tokens.css` or `tokens.json`: colour, type, spacing, radius, motion.
- `components.md`: inventory with states.
- `screens/*.png`: mockups, and later real screenshots.

Process changes:

- **Design gate** for projects with a UI, after the plan gate and before the first UI item. The CEO approves the direction and two or three key screens as images on the phone. Changing a mockup is cheap; changing built UI is not.
- **Visual evidence.** A UI item is not `verified` without screenshots at both widths and an accessibility run with no serious violations. The Head of Design's critique of the screenshots is the review for visual criteria.
- **Default stack**, as an ADR the architect may override with a reason: Next.js, TypeScript, Tailwind, shadcn/ui. Fewer open choices means fewer tokens and more consistent output.
- **Toolchain without breaking the uv-only rule.** Node goes into the project venv with `nodeenv` (`uv pip install nodeenv`, then `nodeenv -p`). Playwright browsers live under the project (`PLAYWRIGHT_BROWSERS_PATH=.venv/ms-playwright`). Needs a Windows spike before it becomes the default.

Done when a small UI-heavy test project (section 4) passes the design gate, and the CEO judges its released screens good from the phone.

### D. Productization team

Turns "it works" into "someone can sign up, pay and get help". Existing roles do most of the execution; the new parts are ownership and a checklist.

- **Head of Productization (new, Fable)** owns `company/launch/readiness.md`, a checklist tailored per product: auth and account lifecycle, multi-tenancy and data isolation, billing (Stripe test mode only), onboarding and empty states, telemetry and error reporting, backups and a restore drill, docs and help, a support channel, a pricing page, draft terms and privacy pages (flagged for a lawyer, never presented as final), deployment and rollback.
- Each unchecked line becomes a backlog item for engineers, DevOps, the design team or the Technical Writer.
- **Launch gate (new)**, distinct from release. Release means "merge this item"; launch means "real customers may use it". `talos gate launch` refuses while readiness lines are open, and approval needs the CEO's words like every gate.

### E. GTM team

- **Head of GTM (new, Fable)** owns the customer profile, positioning, pricing hypotheses, launch plan, and the success metrics the product must instrument. Requirements reach the backlog through the Head of Product: telemetry events, the pricing page, onboarding promises.
- **GTM Analyst (new, Sonnet)** writes competitor teardowns, landing page and email copy drafts, a content calendar, and outreach lists as drafts.
- Split with the Head of Research: Research answers "should we build this" before the charter. GTM answers "who buys it and why" from the charter on.
- Output in `company/gtm/`: `icp.md`, `positioning.md`, `pricing.md`, `launch-plan.md`, `copy/`.
- **Hard rule: Talos drafts, the CEO sends.** GTM roles get Read, Write, Edit, WebSearch and WebFetch only: no Bash, no mail or social connectors. Anything outbound becomes a CEO question with the draft attached.

### F. Opt-in staffing

More roles cost tokens even when idle, because every agent's description loads into every session.

- `template/teams.json` maps teams to agents and skills: `core` (today's roles), `design`, `productization`, `gtm`.
- `init.py --teams core,design` stamps only those. Re-running with more teams adds them. Nothing is removed without `--prune`.
- The kickoff recommends teams in the charter. Agents cannot write under `.claude/` in headless runs, so after the charter gate the CEO, or an interactive session, runs `init.py --teams ...`. The report gives the exact command.
- Agent descriptions get a budget of about 30 words each.

## 4. Phases and how each is proven

| Phase | Contents | Proof |
|---|---|---|
| 0 | A1 to A3 | Reproduces the linkboard table; a report shows a Spend section |
| 1 | B1 to B6, F | **Replay test**: a new brief the size of linkboard, run end to end; tokens per verified item compared with the baseline |
| 2 | C, plus the nodeenv and Playwright spike | **UI test project**: a small app with three or four screens; design gate on the phone; the CEO judges the result |
| 3 | D, E | The real Promethean MDM kickoff: the charter staffs all teams, and GTM and productization produce their first artifacts before the first build cycle |

Each phase ends with a retro and a framework commit, as before. Phases 0 and 1 change the core loop, so they land first and the new teams are built on the cheaper loop.

## 5. Decisions for the CEO

1. **Node for frontends.** Install it into each project's venv with nodeenv, which keeps "only uv and git on the machine", or allow Node as a third machine-level tool? Recommendation: nodeenv, if the spike passes.
2. **Default frontend stack.** Next.js, TypeScript, Tailwind and shadcn/ui as the default ADR? Recommendation: yes.
3. **Design gate.** Mandatory for every project with a UI, or only when the charter says so? Recommendation: mandatory; it is the cheapest point to change direction.
4. **Coordinator on Sonnet (B2).** Run mechanical cycle phases on Sonnet and keep Fable for judgment? Recommendation: yes, judged by the replay test.
5. **Outbound GTM.** Confirm Talos never sends, posts or emails, even later. Recommendation: confirm.
6. **Test projects.** Approve two more test runs, the replay test and the UI test project, before MDM. Recommendation: yes; MDM is too valuable to be the first run of a new loop.

## 6. Risks

- **Transcript format changes.** `talos usage` depends on an undocumented file layout. Mitigation: fail soft, a fixture test, one parser module.
- **Short-lived orchestration loses judgment** that a long session accumulates. Mitigation: `talos status --brief` and the hand-backs carry the state, and the replay test checks report quality, not just tokens.
- **More roles, more handoffs.** Mitigation: opt-in teams, and new teams mostly create backlog items for existing executors.
- **Visual judgment by a model is uneven.** Mitigation: the design gate keeps the CEO's eye on direction, and screenshots on the phone are the final check.
- **Legal drafts mistaken for legal advice.** Mitigation: every terms or privacy draft carries a "draft, needs a lawyer" header, and the launch gate lists it as an open CEO item.
