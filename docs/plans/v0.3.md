# Talos v0.3 plan

Status: draft for CEO review · 2026-10-30 · Author: Claude (Opus 5.5) for the CEO

## 1. Goals

Talos is **plug and play**. Point it at any folder: an empty one, a pile of files that isn't a repo, or a project already under way. A company is employed there straight away and helps with anything: a fix, a feature, a redesign, a launch plan, marketing copy. The target user is a solo developer. Claude Code is the only client in v0.3: it supplies the chat, the subagents and the hooks, and Talos supplies the company, the record and a control room in the browser.

1. **Plug into any folder.** The company works out what is there and builds an accurate, cited picture of the codebase, the product and how the developer works. The CEO corrects that picture at one gate.
2. **A standing company that takes any task.** The kickoff → plan → cycle path becomes one route among several. A one-line fix should not need a charter.
3. **More than engineering.** Design, marketing and GTM, productization and docs are departments the company can staff when a task needs them. Talos drafts and the CEO sends.
4. **Install from git, two ways.** A Claude Code plugin from the GitHub repo (preferred), or a clone plus `uv run init.py`. No PyPI for now.
5. **Fix what v0.2 runs exposed**, and add effort presets so tasks get cheaper and faster. Medium is the default. **Fable runs only on heavy.**
6. **See the company work as an organisation.** A visualizer page that shows who handed what to whom, as a living hierarchy.
7. **Steer it while it runs.** The visualizer becomes a control room with approve buttons, a chat input for thoughts, comments and answers, and a preset switch.

The target first five minutes:

```
/plugin install talos            # once, project scope
/talos                           # in an existing repo
  → "I see a FastAPI app, 14k lines, 212 tests (3 failing). Reading it now, about $4."
  → the understanding report on your phone: correct it or say "approved"
"add CSV export to the reports page"   → a fast-lane item, a branch to approve
"draft launch copy for Product Hunt"   → a draft in company/gtm/copy/, never posted
```

## 2. The journey today, and what changes

| Step | Today | v0.3 |
|---|---|---|
| Install | clone the framework, then run `python init.py` (needs a working Python; on Windows the Store `python` stub breaks it) | `/plugin install` from the GitHub repo, or clone plus `uv run init.py` |
| Where | a repo, with a brief for new work | any folder: empty, not a repo, or an existing repo |
| Describe the work | write a brief file, then choose `--teams` | the company interviews you; for an existing repo it reads the code first and asks only what it can't infer |
| Existing code | not supported: kickoff assumes a greenfield brief | `adopt`: survey, understanding report, baseline, gate |
| Ask for work | run phases in order (`kickoff`, `review`, `plan`, `review`, `cycle`, ...) | say what you want; triage picks the route |
| Next step | `status` reports the state but not what to do next | one verb, `/talos` or `talos`, does the next step or asks for the decision it needs |
| Gates | type `run review "<words>"` | press approve (or reject, with a reason) in the control room, or reply in the conversation |
| Mid-run input | none: a running phase can't hear you | the control room's chat; the running phase reads it at its next checkpoint |
| Cost level | edit `model:` in each agent file | pick lite, medium or heavy in the control room or with `talos preset` |
| Windows | `run`, `talos` and `pyrun` are sh scripts | `.cmd` shims as well, plus `talos doctor` |
| Updates | re-run `init.py`; no version recorded | plugin updates, `.talos/version`, `talos upgrade` lists what changed |

## 3. Workstreams

### A. Plug into any folder

`/talos` in a folder with no `company/` employs a company there. What it does first depends on what it finds:

| Found | First reply | Then |
|---|---|---|
| **Empty folder** | "What are we making?" | an interview in place of a brief, then the Initiative route (today's lifecycle) |
| **Files, but not a git repo** (code, docs, a business folder, design assets) | what it sees, and: "I'll run `git init` here (local only, never pushed) so work happens on branches. OK?" | adopt (below). Until git exists, only the answer and draft routes run, and they write only into `company/` |
| **A git repo** | what it sees, the estimated cost of reading it, and that it's starting | adopt (below) |

**Employed at once, not after a long onboarding.**
- You can ask questions and request drafts from the first reply. Asks queue while adoption runs.
- Fast-lane changes open as soon as the survey and the test baseline are done. Both are scripted, so that takes minutes and costs little.
- Item and Initiative routes wait for the understanding gate, because they rely on the company's picture of the project being right.

**Adoption** runs in four steps, cheapest first.

1. **Survey (a script, no model).** `talos survey` uses only the standard library and writes `company/knowledge/inventory.json`:
   - the file tree and lines of code per language
   - manifests: `package.json`, `pyproject`, `requirements`, `Dockerfile`, compose, CI configs
   - entry points, and candidate test and build commands
   - git history: commit cadence, the most-changed files (hot files), authors as a count only, and branches
   - TODO and FIXME counts, existing `README`, `CLAUDE.md` and docs
   - non-code material: documents, spreadsheets, images, decks, counted by kind
   - size class
   This bounds everything after it: the model reads the map, not the whole folder. A folder with no code skips the baseline step, and its understanding report describes the material and what the company could do with it.
2. **Environment and baseline.** The existing environment probe also runs the test suite once and records which tests pass and which fail (`company/baseline.md`). From then on the rule is **never regress the baseline**: tests that failed before adoption are recorded as known failures, not blamed on the company.
3. **Understanding.**
   - Sonnet analysts read one area each, in parallel, guided by the inventory.
   - The Chief Architect then writes the synthesis in a single pass, with a turn cap:
     - `company/knowledge/codebase.md`: modules, data flow, entry points, where to change what
     - `conventions.md`: style, test layout, commit and branch habits inferred from git, how the developer names things
     - `product.md`: a reverse charter covering what the product does, for whom, and its current state
     - recovered decisions as `ADR-*` marked **recovered, not decided**
     - `debt.md`: debt and risks, each one a candidate item
   - Every claim cites `path:line` or a commit. An uncited claim is a question, not a fact.
4. **Understanding gate.** The CEO receives a one-screen summary with the five questions the company could not answer from the code (audience, priorities, what is off-limits). Corrections become lessons. Approval turns `product.md` into the standing charter.

The company also respects that the repo belongs to the developer:
- It adopts the repo's conventions. It does not reorganize, reformat or migrate unless asked.
- It never works in the developer's checkout. All work happens in worktrees and branches, and a dirty working tree is never touched.
- It keeps up when the developer codes by hand. At the start of every route it compares git history with the last ledger event, and the Librarian (Haiku) refreshes the parts of `codebase.md` for files changed outside the company.
- Cost is capped by size class. The plan targets under $5 to adopt a small repo, and the estimate is shown before step 3 runs.

### B. Standing company: any task, routed

Starting with `/talos <anything>`, `talos ask "<anything>"`, or a plain request in a Claude Code session, the Chief of Staff (on Sonnet for triage) records the ask with its own ITEM id and picks a route.

| Route | When | Path | Gates |
|---|---|---|---|
| **Answer** | a question about the project | read the record and the code, then reply; logged, no item | none |
| **Fast lane** | a contained change: a fix, a small feature, a chore, a doc | inline spec, then executor, then review by risk, then verify | release only |
| **Item** | needs a spec or touches several modules | spec, then the normal cycle for one item | release, plus design if it changes UI direction |
| **Initiative** | a new product area, a redesign, a launch, a migration | mini charter, then plan, then cycles (today's lifecycle, sized by B7) | charter, plan, release |
| **Department** | marketing, GTM, research or docs work with no code | the department lead, then drafts in `company/<dept>/` | the drafts go to the CEO as a question |

- **Triage is visible.** The first reply states the route, the department, the estimated cost and what it will ask the CEO, for example: *"Fast lane, engineering, about $2, you'll approve one branch."* The CEO can override with "make it an initiative" or "just answer".
- **Queue.** Asks queue in `company/queue.md`. `/talos` with no text runs the next one, and the CEO can reorder.
- **Every dispatch names one ITEM id.** This fixes the retro's attribution gap, where 61% of spend could not be traced to an item.
- **Saying no.** Triage refuses or asks when an ask conflicts with the charter, an ADR or an off-limits list. "More no than yes" still holds.

This replaces the lifecycle-only assumption in `talos-cycle`, `talos-status` and `CLAUDE.talos.md`. The lifecycle survives as the Initiative route.

### C. Departments beyond engineering

The productization and GTM teams in v0.2 sections D and E were never built. They are built here, plus a marketing slice:
- **GTM and marketing** (`gtm` team)
  - The Head of GTM covers positioning, ICP, pricing hypotheses and the launch plan.
  - The GTM Analyst drafts landing copy, launch posts, release notes and changelogs, the content calendar, SEO briefs and competitor teardowns.
  - Tools: Read, Write, Edit, WebSearch, WebFetch. No Bash, no connectors. Output goes in `company/gtm/`.
  - Anything outbound is a CEO question with the draft attached. **Talos never sends, posts or emails.**
- **Productization** (`productization` team): the readiness checklist and the launch gate, as specified in v0.2 section D.
- **Design** already exists. It gains the cheap revision path (section E2) and can make marketing visuals (social cards, screenshots of designed states) using `screens.py`.
- **Staffing on demand.** When an ask needs a team that isn't staffed, triage says so and gives the one command or plugin install. A headless session still cannot write under `.claude/`.

### D. Install (Claude Code only, git only)

v0.3 targets Claude Code alone; non-Claude clients are out of scope for now. Installs come from the GitHub repo only, with no PyPI package.

1. **Plugin (preferred).** The repo becomes a marketplace (`.claude-plugin/marketplace.json`).
   - Install at **project scope**, so nothing is system-wide.
   - `/talos` in any folder employs the company (section A): it creates `company/`, vendors `tools/talos/` and writes `.talos/version`.
   - Upgrades come through the plugin, and `talos upgrade` lists what changed since the project's recorded version.
   - One plugin per team or a single plugin is open decision 2.
   - Verify the current plugin spec (layout, scope, hooks, per-agent models) at build time before relying on these details.
2. **Clone plus `uv run init.py`.** Vendored files, pinned and offline. This is today's path, fixed for Windows so it needs no system Python.

The record keeps working without the plugin, because `tools/talos/` is vendored into each project.

### E. Framework updates carried from v0.2 runs

**E3 to E10 built 2026-10-31**, tested with fixture results and no real Claude run. Three things differ from the text below:
- The gate push notification (E10) is not built: a headless phase has no way to send one without an outside service. It moves to the control room.
- The heavy-role warning (E9) is per cycle, not per run, because transcripts are grouped by cycle in `usage.py`.
- A third failed attempt (E6) was already stopped at the second rejection; that stays, and the architect now re-specs in the same cycle.

1. **Effort presets.** Three presets set the model per role. **Medium is the default, and Fable runs only on heavy.**

   | | Executives | Reviewers | Execution | Mechanical | Triage and coordination |
   |---|---|---|---|---|---|
   | lite | Sonnet, with turn caps | Sonnet; Opus for high-risk items only | Sonnet | Haiku | Sonnet |
   | **medium (default)** | Opus | Opus | Sonnet | Haiku | Sonnet |
   | heavy | Fable | Opus | Sonnet | Haiku | Sonnet |

   - Set it with `talos preset lite|medium|heavy` or from the control room (section G). It is stored in the record as a `preset.changed` event, and an ask can override it for one task ("do this one heavy").
   - A change takes effect at the next dispatch, never mid-task.
   - The launcher passes the preset's model to each phase session. Subagent dispatches pass the preset's model for that role, so agent files no longer hard-code `model:`. This matters because a headless session can't edit files under `.claude/`.
   - Fable was 86% of linkboard tokens, and the visualizer plan cost $40 plus $18. The presets are measured with the tempconv replay brief on all three before they ship. The proof is that medium's quality holds (items verified first time, review findings caught) at a fraction of heavy's cost.
2. **Design-revision path.** `run design-revise "<feedback>"` calls only the Head of Design and the UX Designer: they revise the direction and mockups and re-open the design gate. The plan stays as it is unless the architect flags an impact. Target: under a fifth of a plan rerun.
3. **Honest stops.** When `claude -p` ends on a usage limit, the error subtype is recorded as `run.stopped` with a reason, never "STOPPED: success".
4. **Resume.** Hand-backs are written to `company/handbacks/` as they arrive, not at phase end. `run resume` reads the last unfinished phase, takes stock of the worktrees and continues. Uncommitted worktree work is committed to a `wip/` branch before any cleanup.
5. **Verify proof.** `cycle-verify` proves itself only by `item.verified` or an explicit `verify.blocked`, never by `review.changes_requested` alone. Close refuses to run when nothing is verified and nothing is blocked.
6. **Escalation latency.** A third failed attempt goes to the architect for a re-spec automatically. It reaches the CEO only when the spec's intent is ambiguous. (This was the company's own LESSON-0009: 4.5 hours lost waiting.)
7. **Process-kill guard.** The destructive-command guard blocks `taskkill`, `kill` and `Stop-Process` unless the PID is one the company started (recorded in `.talos/pids`). It never kills by port or image name. This is ITEM-0025's incident: about 9 unrelated processes were killed.
8. **Release every cycle.** The cycle report's release question merges on approval right away. Branches are never stacked across cycles, which cost rebases.
9. **UI engineer budget.** A screenshot budget and a context pack for UI work. The launcher warns in the report when any role passes 5M tokens in a run (the UI engineer burned about 23M per cycle).
10. **UX quick wins.**
    - `talos doctor`: checks claude, uv, git, a working Python, PATH inside long-running processes, the trust dialog, and Docker when the charter needs it.
    - `.cmd` shims, and `uv run init.py` in the README.
    - `status` ends with the next step and its estimated cost, from measured runs.
    - At every gate, a push notification with the one-screen report and the visualizer link.
11. **Interview instead of a brief file.** For greenfield work the kickoff asks six questions and writes `brief.md` itself. Teams, size and the visualizer are proposed in the charter, not chosen as flags.

### F. Visualizer: the Canopy page (hierarchy)

**Built 2026-10-30.** Three things differ from the description below:
- Twigs grow from the org chart, not from the dispatching role, because every dispatch in the measured runs came from the phase session (spawn depth 1). A task's card names the session that sent it.
- Pulses show only the roles working right now. Hand-backs and questions are not animated; open gates and questions show as a knot on the trunk.
- The legend does not isolate a tier yet.

The growth rings are a cross-section of the trunk: when things happened. **Canopy** is the tree standing up: who did the work and who handed it to whom. It uses the same visual language as the rings (tier colours, thin lines, slow motion) and gets a fourth sidebar entry with a branching-tree icon.

**The picture**
- **Roots: you.** The CEO sits at the base as a root system. Each root is one thing you gave the company: the brief, an answer, an approval. Gates are drawn as knots where trunk and roots meet.
- **Trunk: orchestration.** The Chief of Staff, the coordinator and the launcher's phase runs. Its girth is the share of spend spent orchestrating, so an expensive main session is visible at a glance.
- **Boughs: the executives.** The Chief Architect, Head of Product, Head of QA, Head of Design and the others. Bough thickness is tokens and length is how long they were active.
- **Twigs: execution and review.** Engineers, the UI engineer, test engineers, reviewers and the Librarian, each growing from the role that dispatched them. Nested dispatches (the depth-2 subagents) grow from twigs.
- **Leaves: individual tasks.** A leaf is one dispatch, such as "Build ITEM-0013 Spend assert". Its size is cost, and its state is drawn as:
  - **verified:** a full leaf
  - **changes requested:** a curled leaf
  - **blocked:** a bud that never opened
  - **failed or abandoned:** a fallen leaf on the ground beneath the tree
- **Fog: unattributed spend.** Spend that can't be traced to an item hangs as haze around the trunk, so the attribution gap becomes something you can see shrink.

**Motion: the relay**
- Delegations travel **up** the tree as a small pulse along the branch: a task sent.
- Hand-backs travel **down** as a returning pulse in a second colour: a result reported.
- Questions to the CEO travel all the way down to the roots and wait there, glowing, until answered.
- While a phase runs, the pulses are live, over the same SSE stream as the rings. Afterwards a **time scrubber** under the tree replays the project: the tree grows branch by branch as roles first get work, and leaves appear in order.

**Lenses**, switched in the page header:
1. **Tree:** the whole company, as described above.
2. **Follow an item:** pick an ITEM, or tap a leaf. Everything else fades, and the item's path lights up as a route: CEO → Chief of Staff → architect (spec) → engineer (build) → reviewer → QA (verify) → release knot. Each handoff shows its time and cost, which shows where an item waited, for example the 4.5-hour escalation.
3. **Relay:** the same handoffs as a baton race, with one lane per role and time running left to right, and the baton line jumping between lanes. It's the plain-reading version of the tree. On a phone it scrolls sideways.

**Interaction**, consistent with the rings:
- Hover or tap a branch for the role card: model and tier, tasks received and sent, tokens and dollars, items verified, lessons cited, and who it reports to.
- Hover or tap a leaf for the task card: the dispatch description, its worktree branch, its outcome event and its cost.
- Click to pin a card; Escape clears it.
- The legend isolates a tier, the same as on the rings.
- Reduced motion: no pulses, with a static tree and arrows instead.

**Where the data comes from** (read-only, standard library, the same rules as the rest of the visualizer):
- Claude Code transcripts already hold the hierarchy. Each subagent's `.meta.json` records:
  - `agentType`: the role
  - `description`: the task
  - `toolUseId`: links it to the parent's Agent call
  - `spawnDepth`, `worktreeBranch`, and whether it finished
  - Parent → child edges and timestamps come from those links, and token cost comes from `usage.py`, which already parses these files.
- The ledger adds the edges the transcripts don't show:
  - `actor` on every event
  - `review.requested` → reviewer
  - `question.asked` → CEO, and its answer back
  - `release.approved` at the gate knot
  - the `item` field, for the follow lens
- A new `viz/hierarchy.py` builds `{nodes, edges, tasks}` and serves it at `/api/hierarchy`, using the same `?p=` project switcher.
- When transcripts are missing (deleted, or from another machine) the page falls back to a ledger-only tree: roles and handoffs without per-task cost.

**What it shows that the rings don't:** where orchestration overhead sits, which role is the bottleneck, rework loops (one leaf curling several times), and fan-out (one architect spec feeding five engineers).

### G. The control room: approve, talk, set the preset

The visualizer stops being view-only. It becomes the place where you steer the company while it works. A new ADR supersedes the visualizer's read-only decision (ADR-0008). `--read-only` keeps today's behaviour for anyone who wants just the view.

**Approve and reject**
- Every open gate (understanding, charter, plan, design, each release branch, launch) shows as a card at the top of every page.
- The card has the one-screen summary, links to what it's approving, and **Approve** and **Reject** buttons. Reject needs a reason.
- A press records the decision exactly as `run review` would, attributed to the CEO and marked as coming from the control room.

**Chat**
- A chat input sits along the bottom of every page, docked above the nav on a phone. You can type anything:
  - **A thought or comment** ("the empty state feels cold", "prefer Postgres from now on"). The Chief of Staff reads it at the next checkpoint and acknowledges it in the thread. It then becomes a correction to the running task, a new item, or a lesson, and the reply says which.
  - **An answer.** Open questions appear in the thread with a reply box, so answering one unblocks the item that was waiting on it.
  - **A new task.** It goes to triage (section B) and joins the queue.
  - **Pause or stop.** The runner stops at the next checkpoint and never mid-write.
- The company's side of the thread is the ledger events addressed to you: questions, gate requests, reports and acknowledgements. The chat is a view over the record, not a second store.
- **How a running phase hears you.**
  - Messages go to `company/inbox.jsonl` through the CLI (`talos say`).
  - A hook in the running session checks the inbox after each tool call and adds unread messages to the session's context.
  - The skills also read the inbox between dispatches.
  - Verify at build time that the hook can inject context. If it can't, the between-dispatch check alone is the fallback, with a slower response.

**Preset switch**
- A three-way control (lite · medium · heavy) in the header shows the estimated cost per item next to each preset, from this project's measured runs.
- Changing it records `preset.changed` and takes effect at the next dispatch.

**Who acts on a press**
- The control room only writes to the record. It never starts processes or runs Claude.
- A runner, `talos work`, runs the queue, waits at gates and continues when it sees the decision. The CEO starts it in a terminal or a Claude Code session.
- If no runner is active, the header says so, and approvals wait in the record.

**Security, now that it writes**
- Writes are POST-only, to a handful of endpoints. Each maps to one CLI command with validated arguments and no shell.
- A secret is generated at every start and printed as a link (`?k=...`). That sets a cookie, and every POST needs it.
- The server checks the Origin header, keeps the host allow-list, and binds to 127.0.0.1 unless `--host` is given.
- Nothing typed in the chat is ever run as a command. Chat text is data the company reads, and the same rules apply as for any observed content.

## 4. Phases and how each is proven

Tests stay tiny, as decided in v0.2 (decision 6).

| Phase | Contents | Proof |
|---|---|---|
| 0 | E3 to E10 (fixes, guards, doctor, shims, next step) | unit tests; `doctor` on this machine; a usage-limit stop simulated with a fixture result |
| 1 | E1 presets, E2 design revision, G control room (approve, chat, preset, `talos work`) | the tempconv replay brief on lite, medium and heavy; one design revision on the focus-timer test project; on a scratch project, approve a gate and answer a question from the phone, and a comment typed mid-cycle is acknowledged by the running phase |
| 2 | A (plug into any folder, adopt) | three scratch folders: empty, files without git, and a **copy** of a small real repo (open decision 1). Each gets the right first reply, and the repo copy passes the understanding gate with few corrections, its baseline recorded, within the size cap |
| 3 | B and C (routes, departments) | three asks on the adopted copy: a fix (fast lane), a UI tweak (design-revision path), and launch copy (GTM draft, never sent) |
| any | F (Canopy page): independent of the other phases | built directly 2026-10-30 after the CEO liked the mockup, checked by eye against the visualizer project's record (ITEM-0013 follows its real path, including the 5h04m wait), with light server and UI tests |
| 4 | D (plugin, git clone path) | install the plugin into a fresh scratch folder that is not a repo, run `/talos`, and get to a first fast-lane change |

Order of work:
- Phase 0 first, so everything after it runs on a loop that stops honestly and resumes.
- Adopt comes before any-task, because triage needs the knowledge adopt produces.
- The control room lands with presets in phase 1, so every later test is steered from it.
- Packaging comes last. From phase 0 on, new files go where the plugin layout will want them, so phase 4 moves files rather than rewriting them.

Each phase ends with a retro and a framework commit.

## Phase 1 results (2026-10-31)

**Presets, measured.** The tempconv brief, run once per preset, end to end. `talos work` ran the phases and every decision went through the control room's HTTP endpoints. One run each on a tiny project: this shows direction, not a precise ratio.

| | lite | medium | heavy |
|---|---|---|---|
| Cost | $2.90 | $6.75 | $14.95 |
| Time | 18 min | 36 min | 40 min |
| Tokens | 4.11M | 5.29M | 6.65M |
| Plan phase | $0.32 | $2.96 | $5.52 |
| Items shipped | 2 | 2 | 3 (README as its own item) |
| Sent back in review | 0 | 0 | 2, both about a test file's first line and a test not being rerun |
| Result of `tempconv 1e308 C F` | prints `inf`; security review caught it, became a proposed item, not fixed | clear error, exit 2 | prints `inf`; not caught |
| Tests in the delivered tool | 15 | 51 | 26 |

- Medium is the default on this evidence: it cost 45% of heavy and its result was as good or better. Heavy's extra spend did not show up in the product here. A tiny tool can't show whether Fable plans better on hard work, so heavy stays available.
- Each role ran on the model its preset names, read from the transcripts. Fable appeared only on heavy. On lite, reviewers ran on Opus for the high-risk item as designed.
- Comparing with the v0.2 replay ($15.95 at medium planning depth on Fable): same brief, not the same framework, so only a rough guide.

**Mid-run messages.** Verified with a real session: the hook's text reaches a running phase's context. In all three replays a comment sent 45 seconds into cycle-build was acknowledged with what it became. On lite and medium it became a proposed item that no one then built, because proposed items wait for the CEO. A small request probably deserves better; that is for section B's routing.

**Design revision.** On a copy of the focus-timer project: $1.56 against $12.54 for its plan, 12%, under the one-fifth target. The gate re-opened, no spec changed, and the revision reported the work approval would add.

**Not built or not proven**
- `talos work` was exercised on a tiny core-team project only, not with the design gate or a long cycle.
- A preset change while a phase runs is delivered by the same hook, but no real run tested it.
- Approve and reject were exercised through HTTP and in a browser, but not from a real phone yet.
- `init.py` keeps existing agent files, so a project stamped before this keeps `model: fable` as its fallback. The launcher's preset note overrides it on each dispatch if the session follows the note. A proper upgrade path belongs to phase 4.

## Phase 2 results (2026-10-31)

Decided while building: the test repo is a clone of a private project (open decision 1); `git init` asks first in a folder with files (open decision 4). An empty folder gets git without asking once its charter is approved, because nothing of the CEO's is there.

| Folder | First reply | What happened | Cost |
|---|---|---|---|
| Empty | "What are we making?" | answer became a brief, then a proposed charter | run stopped by the test at the charter; about a kickoff |
| Three files, no git | what it sees, and asks about `git init` | no repo until "yes"; then local git, no remote, their files kept; understanding gate reached; it spotted that the notes claim 20 customers and the data shows 2 | $0.29 on lite |
| Clone of a 16k-line repo | what it sees, cost estimate, cap | survey, then understanding gate on medium | $2.82, under the $5 target |

**Understanding quality.** 145 citations: 133 resolve as written and 12 use shortened file names in tables. Five facts spot-checked against the code were right. The five questions were specific to the project. Whether it is right about the product is for the repo's owner to say: the gate has not been passed by anyone who knows it.

**Incident: the baseline ran an unread test suite in the open.** That repo's default pytest run targets a live server and writes to it. The first baseline ran it for 600 s with the network on. A replay with every connection blocked and logged sat for 15 minutes importing `conftest.py` without starting a test or trying a connection, so the real run very probably never reached it. That is evidence, not proof. The company's own report caught this, unprompted, as its top risk.

Fixed: a baseline blocks every connection including localhost, strips credentials from the environment, and does not run a suite it cannot block (anything but pytest). The first reply names real hosts found in test files. Still not covered: a subprocess a suite starts is outside the Python block, though it has no credentials.

**Not met or not proven**
- This repo got no baseline: its suite hangs at import on this machine, and `baseline.md` says so. Baselines were proven on small test repos only.
- Node, Go and Rust projects get no baseline at all until a safe way to run them exists.
- Keeping up with hand-written commits, asks queued during adoption, and any actual work after the gate all belong to phase 3.

**The real run, on lite.** A small repo (the tempconv tool, about 180 lines), stamped with `--protect main`, adopted, then given a question, a fix and launch copy in one go, with a hand commit on `main` first.

Adopting that repo cost $0.31. After the release, `main` was exactly the developer's last commit and still printed `inf`; `talos/work` printed the error with exit 2. The checkout stayed on `main` with nothing changed, and the repo has no remote.

**The branch rule.** `talos protect main`, or `init.py --protect main`. Work and approved releases go on a local `talos/work` branch; the framework's own commit goes there too, made without touching the checkout, and only the CEO merges further. Enforced twice: the session guard refuses merges, commits, pushes and ref updates aimed at the branch, and local git hooks refuse commits, merge commits and pushes from Claude Code shells. The developer's own terminal is not affected.

**What the first run caught.** The test engineer logged `item.verified` as a bare event, which left the status behind with no evidence, so an approved release never merged and nothing said so. `talos log` now refuses those events. Triage items kept a `_TBD_` criterion; the librarian step was skipped when a hand commit arrived. Both fixed; the rerun refreshed the record and logged `drift.seen`.

**Differs from section B**
- The way in is `talos say`, which the chat already used; `talos ask` stays a question for the CEO.
- There is no `company/queue.md`. `talos queue` lists asks from the backlog, and priority orders them.
- An initiative has no mini charter: its plan gate carries the scope.
- Messages during a run: a correction to the running work is acted on; anything else waits for triage, so new requests get built instead of parked as proposed items.

**Also added**
- `talos test` and a guard: when a project's tests name real hosts, a direct `pytest` or `npm test` is refused and the suite runs only with the network blocked. Without this, a test engineer could run a suite that targets a live server.
- Charter: the CEO's words go first, the "Not known" section goes, and messages sent before approval are included. Adoption questions ask one thing each, and one asks whether work may merge into main.
- `gtm` and `productization` teams, with `talos gate launch` refusing open readiness lines.

**Not proven**
- Only the fast lane, answer, department and design routes had a real run, each once, on lite, on tiny projects. The item and initiative routes and the productization role have unit tests only.
- The real run never tried to touch `main`, so the guard and hooks were shown by unit tests, not by stopping a real agent. A fast-forward merge is stopped only by the guard, because this machine's git (2.27) can't run the hook that would catch it, and a command hidden inside a script can get past the guard.
- A message sent during a real phase was not retested with the new wording.
- The cost in triage's first reply is rough: it said about $2 and the fix cost $0.38. The adoption estimate said $2 to $5 and it cost $0.31.
- With a protected branch the `company/` record is not committed anywhere after the stamp; it lives only in the folder.
- Protection is opt-in. An existing repo stamped without it still gets one local commit on the current branch.

## 6. Risks

- **Wrong understanding, confidently written.** Mitigation: every claim is cited, recovered ADRs are marked as not decided, the understanding gate exists, and corrections become lessons.
- **Adopting a large repo gets expensive.** Mitigation: the script survey bounds what the model reads, the size class sets a hard cap, and the estimate is shown before the model runs.
- **The developer and the company edit at once.** Mitigation: the company works in worktrees only, never in the developer's checkout, and detects changes made outside it at the start of each route.
- **"Any task" invites scope creep.** Mitigation: triage states the route and cost first, can refuse, and the charter's off-limits list is enforced.
- **The control room is now a write surface.** Mitigation: a per-start secret, an Origin check and the host allow-list; a few POST endpoints, each mapping to one validated CLI command; chat text is never executed; `--read-only` stays available.
- **Mid-run comments misread or missed.** Mitigation: every message gets an acknowledgement in the thread saying what it became; an unacknowledged message shows as pending; pause and stop are honoured only at checkpoints, never mid-write.
- **Medium (Opus executives) plans worse than Fable.** Mitigation: measured on the replay brief before it becomes the default; heavy is one switch away, per project or per ask.
- **Plugin spec drift.** Mitigation: the vendored record CLI works without the plugin, and clone plus `init.py` stays supported.
- **Marketing drafts mistaken for sent posts.** Mitigation: the hard no-send rule, a "DRAFT" header on every outbound artifact, and GTM roles without Bash or connectors.
